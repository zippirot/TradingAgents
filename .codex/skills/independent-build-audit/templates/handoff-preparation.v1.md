Prepare a factual handoff for an independent engineering auditor of the frozen build candidate. State the actual completion and acceptance status; audit preparation alone does not establish completion. Describe the repository context the executor actually exposes rather than assuming direct repository access.

This is orientation, not an assessment of your work. Do not defend or praise the implementation, grade it, or ask the auditor to trust your conclusions. State only evidence-backed facts and label uncertainty.

Identify whether this is final build acceptance or an explicitly requested interim review. For final acceptance, point to the first decisive application-path proof and the final candidate's affected repetition (or unchanged-source evidence), including the assertion that establishes the promised behavior and the realistic changed-boundary failure/recovery exercised. Distinguish required missing proof from separately approved release deferrals. Reuse the existing evidence report; do not invent results or create another acceptance framework.

Establish the stage (feature source, local combined candidate, or published staging) and exact SHA. List the CI workflow and package test definitions, unresolved relevant failures, selected versus complete suites, exclusions, and exact-SHA CI run states before accepting the builder's verification list. A cancelled or absent run is unverified. If local publication is explicitly deferred, state that local checks can support only local acceptance.

Use these sections:

1. **Approved objective** — the primary intended user or system outcome.
2. **Governing requirements** — the approved plan and material requirements, with references to designs, repository instructions, acceptance criteria, architecture decisions, and approved changes. Separate original requirements, approved implementation changes, approved deferrals, superseded requirements, and unapproved assumptions. Identify the dated authoritative current-status statement; preserve historical evidence without treating it as new acceptance.
3. **Build scope** — implementation period; start and end commits; included commits and branches; uncommitted changes. If the start is uncertain, say so and give the best-supported boundary.
4. **Implementation summary** — for each material requirement, name the relevant components, approach, intended runtime behavior, and anything changed, deferred, narrowed, or not implemented. Do not present planned work as complete.
5. **End-to-end runtime path** — trace the real trigger through UI/external entry point, API/controller, domain logic, workers/queues/jobs, external services, database reads/writes, and final visible or persisted result. Identify every part not exercised through its real entry point.
6. **Changed code and available context** — created, modified, and deleted files; migrations/schema/config/environment/dependency/API/shared-type changes; tests added or changed; and important unchanged callers, safeguards, and predecessor schema in the runtime path. Identify which exact-commit source and evidence content is accessible to the auditor, which is only referenced, and any omitted or truncated content. A local path alone is not evidence of auditor access.
7. **Verification performed** — for every completed check, give the command/procedure, exact commit and environment, material outcome and actual application path exercised, result, relevant evidence, and check type (end-to-end, integration, unit, static, build, or manual). Distinguish implemented, integrated, installed, and operationally verified status. Identify prepared rows, mocked producers, and lifecycle steps omitted by a fixture. Include relevant startup, build, type/lint/test, migration, browser/API/worker, and application/service log evidence when applicable. Report only verification actually performed. Give full-suite and exact-SHA CI results separately from selected suites; name failed, cancelled, missing and superseding runs with IDs/URLs when known.
8. **Unverified areas and limitations** — untested behavior, unavailable services, unrun checks, environment differences, mocked dependencies, coverage gaps, TODOs, known defects, lower-confidence areas, and deployment/migration steps not performed.
9. **Auditor attention areas** — explain why complex logic, integrations, data integrity, auth, security, migrations, concurrency, caching, async work, retries, compatibility, deployment behavior, or implementation assumptions need independent scrutiny. Do not state that they are correct.

For relevant known failure mechanisms, name the existing regression and new contract/sibling case covered. Identify the complete source chain actually supplied, including unchanged error classifiers or saved-output consumers. List missing bodies explicitly; a changed filename is not evidence its complete behavior reached the auditor.
For frozen evidence, identify the explicit hashed paths that deliver workflow/package definitions and bounded exact-SHA receipts. Distinguish supplied receipts from independent test/CI execution, which this runner cannot perform. Do not imply the auditor can fetch linked GitHub logs or read an external artifact merely because a path is cited.
